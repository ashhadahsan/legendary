refresh_cache had the identical serial bug warm_cache did: fetching 40 keys serially (40 * 0.01s = 0.4s) blew the 0.30s deadline in tests/test_refresh.py. Fixed the same way — fetch concurrently via ThreadPoolExecutor(max_workers=min(MAX_CONCURRENT_WORKERS, len(keys))) and assign results with zip(keys, executor.map(_fetch, keys)) to preserve key ordering. MAX_CONCURRENT_WORKERS=4 so runtime ~0.1s. The tests/conftest.py autouse fixture watches threading.active_count() and raises ConcurrencyLimitExceeded if peak > 4, so pool size MUST stay <= 4 (ThreadPoolExecutor caps live threads at max_workers). Guarded with `if keys:` so an empty list doesn't create a zero-worker pool. See [[mem-5f58af5b]] for the warm_cache fix.
